Fitnpulse · Web App UI/UX Case Study

The same product,
rebuilt for the desktop.

Track. Improve. Achieve.

Fitnpulse is one product with two presentations. The phone app stacks cards in a 430 px column; the web app turns the identical data into a sidebar + dashboard built on a 12-column grid. This case study walks the whole web presentation — type, color, themes, the first-run flow, the dashboard, components, motion, responsive behaviour and the live product.

02 · Typography

Two families, one voice.

The web app inherits the brand's type system unchanged: Outfit carries every interface label, number and heading, while DM Sans handles reading text. Sizes are tuned for a pointer device: a 22 px page title, 15 px card titles, 14.5 px navigation and 13–13.5 px body copy.

Why it works: numerals use tabular figures so the step count counts up without the layout twitching, and the two families separate structure from reading even at 12 px inside dense widget grids.

03 · Color System

One token set, two themes.

Every colour in the web app is a --fp-* token, which is why the light and dark themes ship from the same components. Each swatch shows the light value next to the dark-mode value it maps to.

Emerald accent--fp-accent Primary buttons, active navigation, goal progress
Cyan accent--fp-accent-2 Secondary CTAs, links, AI insight accent
Lime--fp-lime Success, low stress, best-day summaries
Orange--fp-orange Calories, streaks, challenge countdowns
Red--fp-red Heart rate, destructive actions, stop workout
Purple--fp-purple Sleep stages, personal records
Pink--fp-pink HIIT category, high-intensity sessions
Brand ramplogo · glows Gradient mark and the aurora glows behind the glass
Surfaces & glass: dark mode paints solid --fp-glass / --fp-glass-2 surfaces over the animated gradient, while light mode runs far more transparent (28% / 42%) so the aurora reads through the frosted panels.
04 · Dark + Light Web Theme

One interface, two visual modes.

Layout and content never move. Only the --fp-* tokens change: background gradient, glass surfaces, text, muted text, borders, accents and glows. The real app persists the choice and crossfades the surfaces over ~300 ms — and every web-app screen on this page now flips on its own 5 s cycle, so you can watch both modes without touching anything. The two frames here stay pinned, one light and one dark, so the comparison never moves.

05 · Web Application

What the web app actually is.

Not a separate product and not a port of the phone screens. The same data module, the same handlers, the same features — rearranged for a pointer, a wide viewport and a keyboard. Four product areas sit in the sidebar; the rest are secondary routes opened from inside them.

🏠
Home

Greeting, today's steps with the weekly chart, five daily metrics, AI insights, the weekly challenge and the start-workout entry.

📊
Progress

Period switcher, monthly totals, the weight trend area chart, BMI, the AI monthly summary and achievement badges.

👥
Community

Challenges, the weekly leaderboard, the friends feed and the invite / share actions.

👤
Account

Profile, personal records, goals, device sync, subscription, privacy and settings.

Shared data module: both renderers read one data.ts, so the web dashboard can never drift from the phone app — the numbers, labels, states and handlers are literally the same objects.

10 · Web Animations & Motion

Every animation has a job.

The timing scale is the one the product already documents: 150–200 ms micro-interactions, 250–350 ms component transitions and 300–450 ms screen transitions. Each tile below is a real interaction you can trigger here.

Hover & press · 150 ms

Buttons lift 2 px on hover and compress to 0.97 on press, with the gradient glow deepening behind them.

Toggle · 250 ms

Settings toggles slide the knob across 250 ms; a row never changes size, so the list never reflows under the cursor.

Notifications 4

The popover keeps a scrim, so the page behind stays visible but inert.

Popover · 250–350 ms

Anchored popovers fade and settle; the page behind is dimmed by a scrim rather than a modal.

Count-up & feedback · 1400 ms

Numbers count up once, when the widget first enters the viewport, then stay put.

Chart draw · 900 ms

Bars grow from the baseline with a 70 ms stagger; the current day is filled with the accent gradient.

11 · Responsive Design

Three layouts, one app.

The app measures the window and picks a layout before it paints: the web shell on large screens, a compact icon rail on tablets, and the untouched phone design below 768 px. Pick a viewport below — this is the same branching the product performs.

Breakpoints: < 768 phone · 768–1024 tablet · > 1024 desktop, with 1025–1400 px treated as tablet on coarse-pointer devices. An ?embed=1 flag (used by the 3D showcase) always forces the phone layout, whatever the frame size.

14 · Design Consistency

Rules that keep two UIs honest.

Because the phone and web presentations live in the same product, the decisions below are enforced on both sides rather than reinvented per screen.

1
Tokens, never raw hex

Components read --fp-* variables, so a new surface or a theme change is a token edit rather than a sweep through the screens.

2
One source of truth

Steps, metrics, challenges, the leaderboard, records and settings all come from a single data module that both renderers consume.

3
Colour means something

Emerald is progress, cyan is AI and sync, red is heart rate and destructive actions, purple is sleep. The palette is never decorative.

4
One timing scale

150–200 / 250–350 / 300–450 ms, with ease-out for entrances and ease-in-out for state changes — identical on both platforms.

5
Same words, same place

“Weekly 70K”, “3 days left” and “Resting · Normal” are the same strings on both platforms, so nothing has to be re-learned.

6
Progressive enhancement

Charts animate only when the data arrives; toggles, sheets and popovers are the same components at every size.

7
Accessible by default

Visible focus rings, 44 px hit targets in the web chrome, semantic headings per region, and full prefers-reduced-motion support.

8
Graceful hand-off

The same URL serves the phone, tablet, desktop and embedded presentation — the layout is chosen at runtime, never forked into separate builds.
